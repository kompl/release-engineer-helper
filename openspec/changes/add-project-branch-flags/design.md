## Context

Сегодня область анализа зашита в два места конфига: `skip_parse` решает, стартовать ли с парсинга лога, а `input.repo_branches_file` задаёт файл со списком репозиториев и веток. `cmd/bambai/main.go` читает эти значения и строит `map[string][]string`, который дальше веером расходится по горутинам Collect → Analyze → Enrich (`cmd/bambai/main.go:105-136`).

Справочник `projects.json` уже лежит в репозитории и содержит полный перечень проектов с их ветками в том же формате `map[repo][]branch`, но тулой не читается — он существует как шпаргалка для человека, который правит `repo_branches.json` руками.

Изменение целиком локализовано в композиционном корне: фазы Collect/Analyze/Enrich/Render получают ровно ту же структуру данных, что и раньше, и о новых флагах не знают. Архитектурное правило «фазы не импортируют друг друга, все фазы видит только оркестратор» сохраняется без правок `.go-arch-lint.yml`.

## Goals / Non-Goals

**Goals:**
- Получать отчёт по одному проекту (или по конкретным его веткам) одной командой, не редактируя файлы.
- Сделать точку входа в пайплайн явной и видимой в команде запуска, а не спрятанной в булевом ключе конфига.
- Оставить `repo_branches.json` нетронутым при точечных запусках — файл перестаёт быть «черновиком под текущий вопрос».
- Держать логику разрешения области чистой функцией, покрываемой unit-тестами без сети и MongoDB.

**Non-Goals:**
- Множественный выбор проектов (`-p a -p b`) — сознательно ограничиваемся одним; для нескольких проектов остаются `--by-json` и `--by-log`.
- Валидация веток по GitHub API или по `projects.json` — `-b` собирается как есть.
- Автогенерация и обновление `projects.json` — справочник ведётся вручную.
- Переопределение путей к логу/JSON из командной строки — пути живут в конфиге.

## Decisions

### Разбор флагов — stdlib `flag` с двумя кастомными `flag.Value`

Проект использует только stdlib (`flag` в `cmd/bambai/main.go:84`), и добавлять `spf13/pflag` ради двух флагов не нужно. Go-шный `flag` уже принимает и `-project`, и `--project` как одно и то же имя, поэтому пара «короткий/длинный» делается регистрацией двух имён на одну и ту же переменную.

Повторяемость `-b` и запрет второго `-p` stdlib не даёт из коробки, поэтому вводится один общий тип-накопитель:

```go
type stringList []string

func (l *stringList) String() string     { return strings.Join(*l, ",") }
func (l *stringList) Set(v string) error { *l = append(*l, v); return nil }
```

`-p`/`--project` и `-b`/`--branch` регистрируются через `flag.Var` на два таких накопителя. Ограничение «максимум один `-p`» становится проверкой `len(projects) > 1` в валидации — вместе с остальными правилами, в одном месте, с единообразным сообщением об ошибке.

*Альтернатива:* `flag.StringVar` для `-p` — тогда второй `-p` молча перетирает первый, и пользователь получает отчёт не по тому проекту, о котором просил. Отвергнуто: молчаливая потеря аргумента хуже явной ошибки.

### Три режима — одно перечисление, одна точка валидации

Флаги сворачиваются в перечисление `scopeMode` (`modeByJSON` | `modeByLog` | `modeProject`) на этапе валидации, до любых побочных эффектов (до чтения конфига в части входных файлов, до подключения к MongoDB, до похода в GitHub). Дальше пайплайн ветвится ровно один раз — по значению режима.

Правила валидации собраны в одну функцию и проверяются в фиксированном порядке:
1. `--by-log` и `--by-json` вместе → ошибка.
2. `-p` вместе с любым из `--by-*` → ошибка.
3. `len(projects) > 1` → ошибка.
4. `-b` без `-p` → ошибка.
5. Ничего не задано → `modeByJSON`.

Каждая ошибка печатает `flag.Usage()` с описанием трёх режимов и завершает процесс ненулевым кодом.

*Альтернатива:* разрешить `-p` вместе с `--by-json` как «отфильтруй JSON по проекту». Отвергнуто: `-p` работает от `projects.json`, и смешение двух источников в одном запуске порождает неочевидные пересечения множеств.

### Разрешение области — чистая функция в `cmd/bambai/scope.go`

Новый файл в пакете `main` рядом с оркестратором: тип `runOptions` (режим, проект, ветки), функция валидации флагов и чистая функция разрешения области:

```go
func resolveProjectScope(projects map[string][]string, project string, branches []string) (map[string][]string, error)
```

Функция не читает файлов и не ходит в сеть — на вход получает уже загруженный справочник. Проверка `project` по ключам `projects` и сборка результата (`branches`, а при пустом списке — ветки из справочника) тестируются таблично, без окружения.

Загрузка справочника с диска остаётся снаружи, в `main`, — там же, где сейчас живёт загрузка `repo_branches.json`.

*Альтернатива:* отдельный пакет `scope/`. Отвергнуто: это ~80 строк оркестрационной логики, не переиспользуемой фазами; новый пакет потребовал бы правки `.go-arch-lint.yml` ради нулевой выгоды.

### Чтение `projects.json` — именованная функция в `parse`

Формат справочника совпадает с `repo_branches.json`, поэтому в `parse` выделяется общий приватный декодер, а поверх него — две именованные точки входа: существующая `LoadRepoBranches` и новая `LoadProjects`. Разные имена дают разный текст ошибки («read projects file %s» против «read repo_branches file %s»), а пользователь по сообщению сразу понимает, какой файл не нашёлся.

*Альтернатива:* вызывать `LoadRepoBranches` с путём к `projects.json`. Отвергнуто: сообщение об ошибке врёт про источник, что дороже одной трёхстрочной функции.

### `skip_parse` — удаление поля с предупреждением о миграции

Поле `Config.SkipParse` удаляется из структуры; вместо него остаётся `DeprecatedSkipParse *bool` с тем же тегом `yaml:"skip_parse"`, которое ни на что не влияет, кроме одной строки предупреждения при старте: ключ устарел, точка входа задаётся флагами `--by-log` / `--by-json`. Указатель отличает «ключа нет» от «ключ есть со значением `false`».

Это важно именно для `skip_parse: false`: без предупреждения такой конфиг молча начал бы работать как `--by-json`, то есть пропускать парсинг лога, о котором пользователь просил. `yaml.v3` по умолчанию игнорирует незнакомые ключи, так что удаление поля само по себе конфиг не ломает.

*Альтернатива:* оставить `skip_parse` как источник дефолта, когда флаги не заданы. Отвергнуто: два механизма для одного решения — ровно та неявность, от которой уходим.

### Точечная выборка не касается `repo_branches.json`

В режиме `modeProject` файл `input.repo_branches_file` не читается и не пишется: карта строится из справочника и флагов и живёт только в памяти процесса. Это и есть цель фичи — разовый вопрос не должен оставлять следов в рабочем дереве.

### Новый ключ конфига `input.projects_file`

Добавляется в `InputConfig` рядом с `LogFile` и `RepoBranchesFile`, дефолт `projects.json` прописывается в `config.Load` вместе с остальными дефолтами. Файл читается лениво — только в режиме `modeProject`, поэтому его отсутствие не мешает запускам `--by-json` и `--by-log`.

## Risks / Trade-offs

- **Конфиги со `skip_parse: false` меняют поведение** (перестают парсить лог) → предупреждение при старте с прямым указанием заменить ключ на флаг `--by-log`; в репозитории текущий `config.yaml` содержит `skip_parse: true`, что совпадает с новым дефолтом.
- **Опечатка в `-b` уходит в GitHub API и возвращает пустой результат** («нет данных» вместо явной ошибки) → осознанный размен: ветки, которых нет в справочнике (например, свежая релизная или feature-ветка), должны собираться без правки `projects.json`. Пустой результат виден в прогресс-баре как `— нет данных`.
- **`projects.json` устаревает относительно реального набора веток** → на `-p` без `-b` это даёт лишние ветки в отчёте (собранные впустую) или недостающие; лечится ручным обновлением справочника, `-b` даёт обход без него.
- **Расширение поверхности CLI** — три режима вместо одного ключа конфига → все три взаимоисключающие и описаны в `flag.Usage()`; неверная комбинация падает сразу с usage, а не в середине пайплайна.

## Migration Plan

1. Запуски без флагов и с `skip_parse: true` продолжают работать как раньше — правок не требуется.
2. Запуски, полагавшиеся на `skip_parse: false`, переводятся на явный `bambai --by-log`; строка `skip_parse` удаляется из `config.yaml` и `config.sample.yaml`.
3. В `config.yaml` и `config.sample.yaml` добавляется `input.projects_file: "projects.json"` (можно опустить — дефолт совпадает).
4. `README.md`, `ARCHITECTURE.md` и `CLAUDE.md` обновляются: описание трёх режимов запуска вместо ключа `skip_parse`.

Откат: возврат предыдущей версии бинаря; форматы `repo_branches.json`, `projects.json` и остальных ключей конфига не менялись, кэш MongoDB не затрагивается.

## Open Questions

- Нужен ли `-p` с несколькими проектами в будущем (`-p a -p b`)? Сейчас сознательно запрещён; если сценарий появится, ограничение снимается заменой одной проверки — формат области `map[repo][]branch` его уже выдерживает.
